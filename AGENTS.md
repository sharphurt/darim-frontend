# Darim: основной интерфейс

Этот репозиторий (https://github.com/sharphurt/darim-frontend) содержит основной развиваемый интерфейс Darim на React/JavaScript/Vite.

Backend: https://github.com/tripples25/darim.

## Задачи в Linear

Если по ходу работы необходимо завести задачу, используй общий проект [Darim в Linear](https://linear.app/tripples25/project/darim-4daa1e866639) (команда `hype-ny`, ключ команды `HYPE`, идентификатор проекта `P-HYPE-3`) для обоих репозиториев. Перед созданием проверь, нет ли уже подходящей задачи; в описании укажи затронутый репозиторий или оба репозитория и ожидаемый результат.

## Направление разработки

От Razor/Blazor-фронтенда в backend-репозитории отказываемся. Новые экраны и изменения интерфейса реализуй здесь. Старый `Wishlist.Client` сохраняется на время перехода; его удаление и отключение требуют отдельной задачи.

## Работа с backend

- Перед изменением пользовательского сценария прочитай `AGENTS.md` backend-репозитория и проверь реальные endpoints и `src/Wishlist.Contracts`. Не придумывай API по старому интерфейсу или макету.
- Согласуй изменения запросов, ответов, авторизации, CSRF и обработки ошибок с сервером. Бизнес-правила и приватность должны обеспечиваться сервером.
- Найди checkout backend в доступном рабочем окружении. Не полагайся на фиксированный путь, в том числе при работе в worktree. Если checkout недоступен, явно сообщи об ограничении проверки. Не клонируй и не переключай чужие ветки автоматически.
- Это отдельные Git-репозитории: проверяй состояние каждого, делай отдельные коммиты и PR, указывай связанные изменения и порядок выкладки.
- Проверки frontend: `npm run lint` и `npm run build`. При изменении API выполни также подходящие серверные проверки. Явно сообщай о непроверенной интеграции.

## Локальная интеграция

Запусти backend по его README на `http://127.0.0.1:5080`, здесь выполни `npm ci` и `npm run dev`. Vite проксирует `/api` и `/auth` на backend (см. `vite.config.js`). Для развёрнутого приложения маршрутизация настраивается отдельно; см. `ops/README.md`.

## Описания изменений для Telegram

Уведомления о выкладке формирует `ops/telegram-ci.sh` из заголовка последнего коммита (первой строки, `%s`), без тела сообщения и описания PR. Поэтому заголовок коммита, запускающего выкладку, должен сам по себе объяснять основной результат изменений; при merge это может быть заголовок merge-коммита.

- Пиши заголовки коммитов по-русски: конкретное действие + затронутый сценарий + существенный результат. Ориентир — одна короткая строка до 100 символов, без потери смысла ради длины.
- Описывай, что пользователь теперь видит или может сделать. Для исправления называй устранённый сбой и условие его возникновения; для инфраструктуры — конкретный результат для эксплуатации.
- Не используй заголовки вроде `fix`, `update`, «Правки», «Обновлён интерфейс» или только имя компонента/номер задачи. Префиксы `fix:`/`feat:` допустимы, но после них должно идти содержательное описание.
- Технические детали, причину, проверки и ограничения раскрывай в теле коммита/PR. Существенный результат обязательно оставляй в первой строке: тело в Telegram не попадёт. Не включай секреты и персональные данные.
- Перед squash или merge проверь итоговый заголовок коммита, который попадёт в ветку выкладки. Если он берётся из заголовка PR, заранее сделай его информативным. Для нескольких изменений выдели основной результат; полный перечень оставь в PR.
- Для задачи в двух репозиториях описывай вклад каждой стороны отдельно; в PR указывай связанную работу и порядок выкладки. Не обещай доступность всего сценария, если для неё ещё нужна выкладка backend.

Примеры: `На карточке желания показан статус бронирования`; `Исправлено открытие списка желаний по прямой ссылке`; `На телефоне кнопка добавления желания доступна без прокрутки`.
