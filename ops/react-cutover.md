# Переход на React

Frontend: `sharphurt/darim-frontend`. API и миграции: `tripples25/darim`.
Этот документ готовит выкладку, а не подтверждает её выполнение. PR backend #13 по надёжности и изменение гостевых броней #2 исключены из этой работы.

## Схема

Публичный HTTPS-домен → Coolify proxy → frontend nginx → backend для `/api/*` и `/auth/*`.
Остальные страницы, включая `/share`, обслуживает React. `/health` проверяет только frontend; здоровье backend проверяется отдельно.

Задать `DARIM_API_UPSTREAM` как доступный из контейнера адрес API со схемой, портом и без завершающего `/`, например `http://darim-api:8080`. Имя `darim-api` — пример: использовать фактический DNS alias backend в общей приватной сети Coolify. В переменную не помещать токены или пароли.

Nginx-конфигурация — шаблон официального nginx entrypoint. `DARIM_API_UPSTREAM` подставляется при запуске. После подстановки проверить `nginx -t`. Backend должен быть доступен до старта nginx. Для обновлений с заменой IP backend перезапускать frontend, чтобы nginx повторно разрешил имя.

Frontend nginx слушает только приватный порт за HTTPS-прокси Coolify. Не публиковать его HTTP-порт напрямую в интернет: входящий `X-Forwarded-Proto` принимается от этого прокси. У backend задать `Proxy__Address` равным фиксированному внутреннему IP nginx. Не доверять всем прокси и сетям. `Host` сохраняется публичным, чтобы Origin, cookie и OIDC callback использовали один домен. Зафиксировать внутренний адрес nginx перед переключением.

## Последовательность

1. Записать текущие digest образов, доменные маршруты и настройки proxy. Подготовить резервную копию штатным процессом. БД и Data Protection keys остаются существующими.
2. На отдельной тестовой БД применить backend-миграцию `OpenEndedSplits`. Она добавляет `SplitOpen` и `JoinOrder`, открывает существующие некупленные распилы. Исторический порядок вступления не был записан: прежние участники получают стабильный порядок по ID, координатор первым. Новые вступления сохраняют фактическую очередь.
3. Развернуть согласованные backend и frontend на тестовом домене. Не подмешивать PR #13. Настроить общий приватный network и доверенный proxy, проверить cookie `Secure`, исходный HTTPS scheme и отсутствие redirect на внутреннее имя.
4. Проверить таблицу сценариев ниже в браузере и Telegram Mini App. Реальные Telegram OIDC и WebView требуют ручной проверки с ботом; поддельный `initData` не подтверждает рабочий вход.
5. После успешных проверок применить миграцию на production штатным CI, обновить API, затем frontend. Переключить основной домен на frontend, сохранив тот же origin для API, auth и фото. Проверить `/api/auth-info`, `/api/me`, вход/выход, CSRF, `/auth/callback`, `/share#...` и фото.
6. Наблюдать ошибки и авторизацию. Blazor не удалять до подтверждённой работы нового интерфейса. Удаление `Wishlist.Client`, его сборки и тестов — последующий отдельный коммит после этого контрольного этапа.

## Откат

Вернуть прежние маршруты домена и сохранённые образы. Не удалять volumes и ключи. Предпочтительно сначала откатывать только frontend, оставляя совместимый API; прежний Blazor не умеет завершать новый сбор, поэтому это временный аварийный интерфейс.

При полном откате API остановить запись. Для возврата старой фиксированной механики установить `Slots = GREATEST(2, число Shares)` у каждого split; затем штатно откатить `OpenEndedSplits`, которая удалит новые поля. Такой откат теряет очередь вступления и состояние открытого сбора, но сохраняет участников и брони. Купленные подарки и внешние брони отдельно сверить до возобновления записи. Не запускать откат миграции при работающих новых экземплярах API.
